# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Sobrô? (the repository is still called JM-Finance-Mobile) is an Expo/React Native (TypeScript) mobile app for personal finance management (income, expenses, balance by category). It is an **online client**: every piece of data lives on the server (a Fastify + Postgres API, in the sibling repository `Sobro - Api`, running on Heroku) and the app reads and writes it over HTTP. A login is required: [app/index.tsx](app/index.tsx) sends a person with a session to `/dashboard` and one without to `/login`. There is no local database and no sync: with no connection a screen says so and offers "Tentar de novo", and nothing is queued to be sent later. Nothing financial is written to the phone's disk; only the session tokens (secure store), the light/dark choice and the "tutorial seen" flag of each account (AsyncStorage) and the reminders scheduled on the phone's own notification system.

## Commands

```bash
npm install          # install dependencies
npx expo start        # start the dev server
npm run android        # run on Android emulator/device (expo run:android, native build)
npm run ios            # run on iOS (Mac only)
npm run web             # Metro web bundler — a first version, see the note below
npm run lint             # expo lint
npx tsc --noEmit          # type check
npm test                   # jest --watchAll
npx jest path/to/file.test.ts   # run a single test file
npm run reset-project       # scripts/reset-project.js (Expo's blank-project reset)
```

`jest-expo` is the preset and `@/` is mapped to the repo root in the jest config, so pure logic can be tested with plain `.test.ts` files next to it (see [utils/insightRules.test.ts](utils/insightRules.test.ts)). Keep tests outside `app/` (like everything that is not a screen), where every file becomes a route. Babel inlines `process.env.EXPO_PUBLIC_*` when it compiles, so a test cannot set the API address at run time: mock `@/api/config` instead (see [api/client.test.ts](api/client.test.ts)).

The app uses `expo-dev-client` and a native Android project that is generated locally (`/android` is gitignored; `npm run android` builds it), so it runs as a development build rather than in Expo Go. After an Expo SDK upgrade the old `android/` folder is stale: regenerate it with `npx expo prebuild --clean` (EAS builds always prebuild from scratch, so nothing may live only in that folder). Native modules (`expo-secure-store`, `expo-crypto`, `@react-native-async-storage/async-storage`, `expo-notifications`, `expo-navigation-bar`, `react-native-reanimated`…) need a new build when they are added. The web target is a first version (a phone-wide column in the browser, see [docs/projeto-web-desktop.md](docs/projeto-web-desktop.md)): `npx expo start --web` runs it and `npx expo export -p web` builds `dist/` (set `EXPO_PUBLIC_API_URL` first; `output` is `single`, so the page comes from [public/index.html](public/index.html), not from an `+html` route). What the browser lacks has a `.web.ts(x)` twin next to the native file (`applyTheme`, `api/tokenStorage`, `WebFrame`); the API must list the site's address in its `CORS_ORIGINS`. The date is chosen with `DatePicker` ([app/components/ui/DatePicker.tsx](app/components/ui/DatePicker.tsx) on the phone; `DatePicker.web.tsx` is a dialog with the browser's date field, because `@react-native-community/datetimepicker` draws nothing on the web). A `Modal` is drawn in a portal on `<body>`, outside `ThemeProvider`'s view, so on the web `useDocumentThemeVars` also sets the color variables on `<html>` (without it a dialog card has no background) and every dialog card has `maxWidth: DIALOG_MAX_WIDTH` so it does not stretch across a wide window; a new dialog must do the same. The browser's focus ring on `input`/`textarea` is turned off in `public/index.html` because `Field` draws its own focus border. Still missing on web: backup export/import and the reminders. Verify UI changes on an Android/iOS build first: the web is a second target, not the reference. Run `npx expo-doctor` after touching dependencies (it passes 21/21 today).

**Platform versions**: Expo SDK 57 (React Native 0.86, React 19.2, TypeScript 6, new architecture only). The SDK is what sets the Android `targetSdkVersion`, which Google Play requires to be 36 for new apps and updates (SDK 52 aimed at 34, 53 at 35, 54 and later at 36), so an SDK upgrade is also a Play deadline matter; keep Expo packages aligned with `npx expo install --fix`, never by hand. Things that changed on the way and are easy to trip on:
- `expo-router` 56+ no longer uses `react-navigation`: take `useFocusEffect`, `useIsFocused`, `useNavigation`… from `expo-router` and never import from `@react-navigation/*` (the packages are not even installed).
- `expo-file-system` default export is the object API (`new File(Paths.cache, name)`, `file.create()`, `file.write()`, `await file.text()`); the old functions (`cacheDirectory`, `writeAsStringAsync`…) throw and live only in `expo-file-system/legacy`.
- `expo-notifications` handler returns `shouldShowBanner` / `shouldShowList` (not `shouldShowAlert`); `Appearance.setColorScheme` takes `'light' | 'dark' | 'unspecified'` (no `null`; `applyTheme` maps "follow the system" to `'unspecified'`).
- The global `fetch` is `expo/fetch` since SDK 56 (set `EXPO_PUBLIC_USE_RN_FETCH=1` in `.env` to go back to React Native's if a request behaves oddly).
- TypeScript 6 no longer includes every `@types/*` on its own: [tsconfig.json](tsconfig.json) lists `"types": ["jest"]`. React 19 types: `useRef<T>(null)` is a `RefObject<T | null>`.
- Jest needs `@react-native/jest-preset` beside `jest-expo`. ESLint (`eslint-config-expo` 57) ships the React Compiler rules; `react-hooks/set-state-in-effect` is off in [.eslintrc.js](.eslintrc.js) because the dialogs reset their fields in an effect when they open.

The API address is `EXPO_PUBLIC_API_URL`, read in one place ([api/config.ts](api/config.ts)). Locally it comes from `.env` (gitignored; copy [.env.example](.env.example); restart with `npx expo start --clear` after changing it) and in an EAS build from the `env` of each profile in [eas.json](eas.json). An Android emulator reaches the computer's own API at `http://10.0.2.2:3000` (clear text works only in a development build).

## Architecture

**Routing**: file-based via `expo-router`. Every folder under [app/](app/) is a route; [app/_layout.tsx](app/_layout.tsx) declares the root `Stack` and must list any new top-level screen folder there **by its full route name** (`wallet/index`, not `wallet`: a short name does not match, logs `No route named ...` and silently drops that screen's options). Route folders follow a consistent internal shape:
- `index.tsx` (or `[id].tsx` for a dynamic route) — the screen itself
- `components/` — the screen's own components, the ones only that screen uses (`app/dashboard/components/CardBalance.tsx`)

Shared, cross-screen components live in [app/components/](app/components/) (including the bottom navigation bar, [sidebar.tsx](app/components/sidebar.tsx), the providers and the account card), with generic/reusable UI primitives further isolated in [app/components/ui/](app/components/ui/) (`Field`, `GradientButton`, `ScreenHeader`, `TransactionList`, `LoadError`, `LoadingBlock`, `InlineError`). A component starts in its screen's `components` folder and moves to `app/components/` when a second screen needs it (`GoalCard` and `GoalFormModal` are there because Carteira and the caixinha sheet both use them).

**What lives outside `app/`**: Expo Router makes a route of every file under `app/` and warns `missing the required default export` in development when one has none, so only screens and components (which all `export default`) go there. Everything else is outside: the types and constants of each screen in [types/](types/)`<screen>/<screen>-type.ts` (the shared ones mirror `app/components/` under [types/components/](types/components/)), the HTTP layer in [api/](api/), the data layer in [db/](db/), and helpers in [utils/](utils/) (`transactionForm.ts`, `applyTheme.ts`). Always put new constants in the `-type.ts`, not inline in components (e.g. [types/editAcount/editAcount-type.ts](types/editAcount/editAcount-type.ts), [types/registrationSpent/registrationSpent-type.ts](types/registrationSpent/registrationSpent-type.ts)). A provider is a component too, so it keeps a default export beside its named one (`FeedbackProvider`, `MonthProvider`, `AuthProvider`, `QueryProvider`). A component under `app/` also shows up as a route nobody navigates to (`/components/sidebar`); that is harmless, and typed routes list it. Import across folders with the `@/` alias (`@/app/components/ui/Field`, `@/types/wallet/wallet-type`), not with `../..`. Adding a screen means: `app/<screen>/index.tsx`, its route in `_layout.tsx`, `app/<screen>/components/` and `types/<screen>/<screen>-type.ts` as needed. Typed routes are generated by `expo start` into `.expo/types`, so a route added since the last run is not known to `tsc` until the dev server runs again (the routes of the access flow are written as `'/login' as any` for that reason).

**Providers** ([app/_layout.tsx](app/_layout.tsx), outermost first): `ThemeProvider` (colors), then, once the saved light/dark choice is applied, `FeedbackProvider` (toasts and confirms), `AuthProvider` (the session), `QueryProvider` (the cache of the API's data), and inside them `SessionGate`, `RecurrenceSync`, `MonthProvider` and the `Stack`. When the server answers 426 (this version is too old) `AuthProvider` sets `upgradeRequired` and the layout draws `UpgradeRequired` instead of the screens.

**Session**: [api/session.ts](api/session.ts) keeps the access and refresh tokens in `expo-secure-store` (the only thing about the account kept on the phone). `AuthProvider` ([app/components/auth/](app/components/auth/)) reads them when the app opens (`status`: `loading` → `signedIn` | `signedOut`; `app/index.tsx` shows just the background while it is `loading`, so the login never flashes for someone already in) and exposes `signIn`, `signUp`, `signOut` and `deleteAccount` through `useAuth()`. The API client tells it when a session ends by itself (the refresh token was refused): it goes to `signedOut` with a toast. `SessionGate` keeps the screen in line with the status: without a session everything but the four screens of the access flow (`login`, `register`, `forgot`, `reset`, in `PUBLIC_ROUTES`) gives way to the login, and with one those give way to the dashboard; it empties the back stack (`dismissAll`) so Back never leads into what the session no longer allows. Ending a session also cancels the scheduled reminders (they carry the names of expenses) and `QueryProvider` empties the cache. Perfil has a "Conta" card (`AccountCard`) with Sair da conta and Excluir conta (a confirm, then a dialog asking for the password: `DELETE /me`; a wrong password is a 401 `invalid_credentials` and shows inside the dialog). The reset-password link of the e-mail carries the token after `#token=`, which the router does not hand over as a parameter: `reset/index` reads it from the URL that opened the app (`expo-linking`) or from a pasted link or code (`utils/authForm.ts`).

**Navigation chrome**: `SideBar` (four tabs, configured in [types/components/sidebar-type.ts](types/components/sidebar-type.ts)) is rendered by each tab screen. Creating a transaction is a separate action: `AddTransactionFab` is rendered next to `SideBar` on Dashboard, Carteira and Detalhamento and opens `registrationSpent`, which `_layout.tsx` declares as a `transparentModal` sheet. That screen is a three-step flow (valor, categoria, detalhes) and draws its own dimmed backdrop. Editing a transaction happens in place on `detailsSpend/[id]` (an input form with a save button; categories and accounts use `PickerSheet`). Screens that show the button use `SCROLL_PADDING_WITH_FAB` as bottom scroll padding so content can scroll past it. A screen with fields wraps them in `KeyboardAvoidingView` with `behavior={KEYBOARD_AVOIDING_BEHAVIOR}` ([types/components/ui/keyboard-type.ts](types/components/ui/keyboard-type.ts), always `'padding'`): with edge-to-edge the Android window no longer shrinks for the keyboard, so the screen makes room itself on both platforms. The dialogs built on `Modal` are another window and were left as they were; check the keyboard in them on a device after changing any.

**Feedback**: never use `Alert.alert`. [app/components/feedback/](app/components/feedback/) provides `FeedbackProvider` (mounted above the `Stack` in `_layout.tsx`) and the `useFeedback()` hook: `showToast({ type: 'success' | 'error' | 'info', title, message? })` for results and warnings, and `await confirm({ title, message, confirmLabel, destructive })` for questions that need an answer. Because the provider sits above the navigator, a toast survives the navigation that follows an action (e.g. the sheet closing after a save). Keep the copy in the screen's `-type.ts`. A toast is drawn behind a `Modal`, so an error of a dialog shows **inside** it (`InlineError`, a `Field` with `error`), never as a toast. `errorToast(error, title)` and `errorMessage(error, fallback)` ([utils/apiErrors.ts](utils/apiErrors.ts)) turn a failed call into a toast or a line: no signal ("Sem conexão"), too many tries (429), the server down (5xx, its text is not shown), or a rule of the server (its `message` is already in Portuguese and says what is wrong). A 400 `validation_failed` shows each `fields[].message` next to its field (`fieldErrors` in [api/errors.ts](api/errors.ts)).

**Styling**: NativeWind v4 (Tailwind for React Native) via `className` props, configured through [tailwind.config.js](tailwind.config.js), [babel.config.js](babel.config.js) (`nativewind/babel` preset, `jsxImportSource: "nativewind"`) and [metro.config.js](metro.config.js) (`withNativeWind`, reading [global.css](global.css)). `className` only becomes a `style` on the components NativeWind knows: those of React Native, and the ones registered with `cssInterop` in [utils/nativewindInterop.ts](utils/nativewindInterop.ts) (imported first by `_layout.tsx`), today just `LinearGradient`. A component from any other library that gets a `className` must be registered there too, or the class is **silently dropped** on a device (no type check, test or bundle notices; [utils/nativewindInterop.test.ts](utils/nativewindInterop.test.ts) guards the one we have). That is exactly what broke the layout after the SDK 57 upgrade: `expo-linear-gradient` stopped being rewritten by the NativeWind Babel plugin, so every gradient (buttons, headers, the account card) lost its padding, height and alignment.

**Dark mode**: the app follows the system's light/dark setting unless the person picks one in Perfil ("Aparência": Automático, Claro or Escuro, saved at once on the phone through [db/theme.ts](db/theme.ts), in AsyncStorage: it is a look, not account data, and it has to be right on the login screens too). `applyTheme` ([utils/applyTheme.ts](utils/applyTheme.ts)) forces the choice with `Appearance.setColorScheme` (null follows the system), so `useColorScheme()`, `useColors()` and the native dialogs all follow it; `_layout.tsx` reads the saved one and applies it before anything is drawn. Design tokens (`primary`, `surface`, `card`, `canvas`, `ink`, `muted`, `subtle`, `line`, `placeholder`, `thumb`, `income`, `expense`, `warning`, plus the `headerGradient`, `buttonGradient` and `disabledGradient` arrays) are defined once, in a light and a dark version, in [constants/palette.ts](constants/palette.ts). `tailwind.config.js` maps each color token to a CSS variable (`rgb(var(--color-canvas) / <alpha-value>)`) and `ThemeProvider` ([components/theme/](app/components/theme/ThemeProvider.tsx), mounted first in `_layout.tsx`) sets the variables of the active scheme with `vars()`, so a class never changes with the theme. Never hardcode a hex color:
- in `className`: `bg-canvas`, `bg-card` (cards, sheets, the tab bar: never `bg-white`), `text-ink`, `text-subtle`, `border-line`, `shadow-primary/40`, …
- in props NativeWind can't reach (icon `color`, `ActivityIndicator`, `placeholderTextColor`, gradient `colors`, `style`): `const colors = useColors()` from [hooks/useColors.ts](hooks/useColors.ts) returns the palette of the active scheme (`colors.primary.DEFAULT`, `colors.placeholder`, `colors.headerGradient`…).
- helpers outside a component that need a theme color (in `-type.ts` files, e.g. `typeColors`, `feedbackStyles`, `insightToneColors`, `toggleThumbStyle`) are functions that take the `Palette`; never read `palette` at module level for something that changes with the theme.
- `palette` itself is the light palette as a plain constant: only for what looks the same in both themes (the blue header band, the FAB, the white text on a filled button, the account colors the person picks).
- a color used as a fill with white text on top is `colors.buttonGradient[0]`, not `colors.primary.DEFAULT` (which is lighter in the dark theme, for text and icons).
- Android draws **edge to edge** and it cannot be turned off (it is enforced for apps aimed at Android 16): the screen goes under the status bar and the navigation bar (gestures or buttons), which are transparent and have no color to set (`expo-navigation-bar`'s `setBackgroundColorAsync` and `StatusBar.setBackgroundColor` are gone or do nothing). What shows behind the navigation bar is the app's tab bar (`bg-card`). Behind the status bar, `ThemeProvider` keeps a fixed strip the height of the bar (the canvas in dark, the card color, white, in light) on top of everything, so what scrolls never passes under the clock and the icons: that is how it always looked. So anything else fixed to the top or bottom edge must add `useSafeAreaInsets()` (`ScreenHeader`, `SideBar`, the floating button, the sheets and `Toast` already do; a new one must too). `useSystemBars` ([hooks/useSystemBars.ts](hooks/useSystemBars.ts), called by `ThemeProvider`) only picks the color of the bars' icons: light in dark and dark in light, for both bars.
- text and icons on the header are `text-headerInk` / `colors.headerInk` (white on the blue band, ink on the dark canvas), never `text-white`.
- the dark look is deliberately not the usual one ("Ardósia"): neutrals lifted out of black (canvas around 11% light) and tinted with the brand blue, in three visible steps (canvas, card, chip) instead of a black slab, the brand blue only as accent and button fill, `income` / `expense` / `warning` in earth pigments (leaf green, urucum red, ochre) instead of mint, coral and amber, no band behind the title (`headerGradient` is the canvas itself), no glow on the FAB (`fabStyle`) and hairline borders instead. Keep new colors in that family and do not reach for emerald, rose or indigo.
- category colors (and the caixinha colors) are the saturated tones the person picked or the catalog brought: the data hooks (`useTransactions`, `useCategoryTotals`, `useCategories`) return them through `softenColor` ([utils/color.ts](utils/color.ts)) on the dark theme, and `useCategoryColor()` does the same for a color that does not come from them. Do not draw a stored category color directly.

Adding a token means adding it to both palettes; [constants/palette.test.ts](constants/palette.test.ts) checks that they match and that text and accent colors keep their contrast on `canvas` and `card`. Changing `tailwind.config.js` or the palette needs `npx expo start --clear`. The dark theme has only been checked by the bundle and the tests, so look at every screen on a device after changing colors.

**Spending bars** (budget of the month, history rows, category limits) share `budgetLevel` / `budgetColor` in [utils/budget.ts](utils/budget.ts): green while more than 20% of the ceiling is left, yellow (`warning`) from 80% spent, red from 90% spent and past the ceiling. The thresholds are in [utils/budget-type.ts](utils/budget-type.ts).

**NativeWind pitfall**: don't add or remove classes after the first render when they use Tailwind's CSS variables (`shadow-*`, `ring-*`, `scale-*`, `translate-*`, gradients). NativeWind then remounts the component and, in dev, crashes with `Couldn't find a navigation context` (it tries to serialize the props for a warning). Put state-dependent shadows, fills and transforms in `style`, and keep `className` constant per component.

**Scrolling screens**: every tab screen (and Perfil and Detalhes) scrolls through [ScreenScroll](app/components/ui/ScreenScroll.tsx), which only scrolls, and only keeps room under the content for the tab bar and floating button (`SCROLL_PADDING_WITH_FAB` / `SCROLL_PADDING_WITH_SIDEBAR`, plus the bottom inset: the bar is taller on a phone with three navigation buttons than with gestures, and a fixed padding left the end of the screen under it), when the content does not fit. A plain `ScrollView` with a fixed bottom padding always scrolled into an empty stretch on short screens. When the content is pulled up over the blue header (`-mt-7`), the header goes *inside* the `ScreenScroll` and the pulled-up content in a wrapper `View`: with a fixed header and a `-mt-7` scroll view, the content is cut off at the header's edge while scrolling, as if the header were swallowing it.

## The API and the data layer

The contract of every route (bodies, answers, error codes) is `api-rotas-e-consumo-mobile.md` in the `Sobro - Api` repository; it wins over anything written here. Two layers sit between a screen and the server:

**HTTP layer** ([api/](api/)): [client.ts](api/client.ts) has `api<T>(method, path, { body, idempotencyKey, auth })`, tested in [client.test.ts](api/client.test.ts). It sends `X-App-Version` (the version of `app.json`) on every call and sets `Content-Type` only when there is a body (the server answers 400 to a JSON content type with nothing in it). An expired access token (401 `unauthorized`) is renewed **once for all the calls that find it expired together** (a shared promise; the refresh token works once, and spending it twice ends the session), and the call is sent again once. It does not renew for `/auth/*`, for a 401 that is not `unauthorized` (a wrong password) or when there is no signal (a missing connection never ends a session). A failed call throws `ApiError` (`status`, `code`, `message`, `fields`) or `NetworkError` (no signal or the 20 s timeout). Its types are in [api/types.ts](api/types.ts) and the route calls of the access flow in [api/auth.ts](api/auth.ts).

**Data layer** ([db/](db/); the folder keeps its old name so the screens did not have to change): [cards.ts](db/cards.ts), [categories.ts](db/categories.ts), [transactions.ts](db/transactions.ts) (also the transfers and the two reports), [recurrences.ts](db/recurrences.ts), [invoices.ts](db/invoices.ts), [budgets.ts](db/budgets.ts), [categoryBudgets.ts](db/categoryBudgets.ts), [goals.ts](db/goals.ts), [profile.ts](db/profile.ts) (the account's profile from `/me` plus the theme of this phone), [backup.ts](db/backup.ts), [reminders.ts](db/reminders.ts) and [theme.ts](db/theme.ts) are plain async functions (no database argument) that call the API and return `*Record` types (`CardRecord`, `TransactionRecord`…). [hooks.ts](db/hooks.ts) has `useCards`, `useTransactions`, `useTransaction`, `useTransferLegs`, `useCategoryTotals`, `useCategories`, `useProfile`, `useInsights`, `useMonthTransactions`, `useBudgetEntries`, `useMonthlyHistory`, `useRecurrences`, `useRecurrence`, `useInvoice`, `useOpenInvoice`, `useFutureMonths`, `useCategoryBudgets`, `useGoals`, `useGoal`: use them in screens rather than fetching in an effect. Each returns its data, `loading` (only until the first answer), `error` and `refetch`, and is built on TanStack Query:
- the cache ([api/queryClient.ts](api/queryClient.ts), provided by `QueryProvider`) is **in memory only**. A screen opens at once with what it last showed and reads again once that is older than 30 s, when the app returns to the foreground, or when something changed. Keys are in [queryKeys.ts](db/queryKeys.ts).
- `useScreenQuery` ([query.ts](db/query.ts)) makes a query run only while its screen is the one in front: screens of a Stack stay mounted behind the top one, and a change made on top (a transaction saved in a sheet) would otherwise refetch every one of them. Behind, a query is only marked old and reads when its screen comes back.
- after anything is saved, edited or deleted call `notifyDataChanged()` ([events.ts](db/events.ts)): it marks every read old and reads again what is on screen (it returns a promise, so `await` it to show the new state before going on). After the account's data was replaced as a whole (a restored backup, where every id changes) call `resetAllData()`.
- `error` is only set when there is **nothing to show** (`loadError`): a refresh that fails behind data already on screen keeps the data. A screen that reads data shows `LoadingBlock` until the first answer and `LoadError` (what went wrong, no signal or server, and "Tentar de novo") when it fails, and never draws zeros as if it had loaded. The form of a save that failed stays as it was.
- every list that grows is read whole: `getTransactions` follows `nextCursor` page by page (up to a safety cap) unless a `limit` asks for just the most recent.

**Money and dates**, the rules that are easy to get wrong ([utils/apiInput.ts](utils/apiInput.ts), with tests): a transaction, a transfer and a recurrence go out with a **positive** `amount` (the `type` gives it its sign) and come back signed (an expense is negative); **only a caixinha movement goes out signed**. A number goes out with two places at most (`centsToAmount`, `roundAmount`). The date of a transaction or transfer is a **calendar day**, sent at noon UTC of the day on the phone (`calendarDayAtNoonUtc`, `2026-10-05T12:00:00.000Z`): never `date.toISOString()`, because at 22h in Brazil it is already tomorrow in UTC and the purchase would land in the next month. A caixinha movement is an instant and is simply left out (the server uses now).

**Creating something is safe to retry**: every `POST` that creates (accounts, categories, transactions, transfers, caixinhas, entries) sends an `Idempotency-Key`, so a "Tentar de novo" after a lost answer cannot make two. A screen gets the key from `useSaveKey()` ([hooks/useSaveKey.ts](hooks/useSaveKey.ts), logic in [utils/saveKey.ts](utils/saveKey.ts)): `keys.keyFor(body)` when the person taps Save (the same key again while the body is the same as the failed attempt's, a new one when the form changed) and `keys.clear()` once it worked. `PATCH`, `PUT` and `DELETE` need none (a repeated delete answers 404, which `deleteTransaction`, `deleteGoalEntry` and the like treat as done).

In the UI a `card` is an **account** ("conta"): a place where the money is (a bank, a card, cash), and the last digits are optional. The code keeps the old names (`cards`, `CardRecord`, `useCards`), so say "conta" in anything the user reads. Accounts are created and edited in Carteira and can be deleted there (`getCardUsage` tells how many transactions and recurrences go with it, `deleteCard` removes them) as long as one is left (409 `last_card`); the account form shows that count as a warning before the delete button, and the confirm dialog repeats it. A card's `balance` is worked out by the server (starting balance + the sum of its transactions) and is never updated directly.

**Path alias**: `@/*` maps to the repo root (see [tsconfig.json](tsconfig.json)), e.g. `import { useCards } from '@/db/hooks'`.

## Screens (route folders under app/)

`login`, `register`, `forgot`, `reset` (the access flow, without a session), then `dashboard`, `wallet`, `myDetailing`, `editAcount`, `registrationSpent`, `insights`, `history`, `search`, `transfer`, `goal/[id]` (a sheet), `invoice/[id]`, `payInvoice/[id]` (a sheet) and `detailsSpend/[id]` (a single dynamic-route file).

Charts use `react-native-gifted-charts` (see `myDetailing/components/ExpenseChart.tsx`); progress bars use `react-native-progress`.

**Dashboard**: the header (greeting on the left, the month pill on the right), the balance card (`CardBalance`, in the app's own light style: Saldo mensal, how it compares with the same stretch of the previous month, and the `Orçamento do mês` bar against the month's budget), a "Fluxo de Caixa" section with the month's entradas and saídas, one insight card, and "Últimas transações". The card shows the month, not the accounts: account balances live in Carteira. The figures come from [utils/summary.ts](utils/summary.ts) (`buildSummary`, covered by its test). There are no flexible spacers: blocks sit at a fixed `SECTION_GAP`, and the list fills a tall screen with more rows (`RECENT_MIN`–`RECENT_MAX`, counted from the measured layout in `app/dashboard/index.tsx`) instead of with empty space. The `RECENT_*_HEIGHT` constants in `dashboard-type.ts` mirror the row and title sizes of `RecentTransactions`; update them together. While the month loads the cards are a spinner, and if it cannot be read, a `LoadError` (a balance of zero would be a lie).

**Detalhamento** ([app/myDetailing/](app/myDetailing/)): one screen with little on it at a time. The blue `MonthlyProgress` (the month's spending against its budget, one line saying where it stands), `CategorySection` (a small donut with the three biggest categories named by share and "mais N"; the whole list with value and limit of each opens in place with "Ver as N categorias", and a category past its limit is told in one line even closed), `PaymentSplitCard` (a line with a small bar that opens into the figures of how it was paid) and `DayGroupedList` (the month's spending in one card, a day at a time, showing the first 5 until "Mostrar mais lançamentos"). No tabs and no filter besides the account one. The rows of the categories come from `buildCategoryRows` ([utils/categoryRows.ts](utils/categoryRows.ts): every category with spending plus those that only have a limit, biggest first; `legendOf` and `overLimit` are the legend and the alert) and the days from `groupByDay` ([utils/dayGroups.ts](utils/dayGroups.ts)); both are covered by tests. Limits are set by tapping a row of the opened list or "Definir limite" (only in the current month and with every account in view, like before), through `LimitSheet`.

**Months and history**: every tab screen looks at one month, held by `MonthProvider` (mounted above the `Stack`; read it with `useSelectedMonth()`). It follows the calendar, so a new month starts empty on its own, until another is picked from the history; nothing is ever deleted, and the accounts' balance keeps accumulating (only the month's figures restart). `MonthPill` (in the Dashboard header, and under the title on Carteira and Detalhamento) shows the month and opens the `history` route, a sheet like `insights` listing every month with what was left, entradas, saídas and the use of that month's budget; picking one calls `setMonth`. Months are 'YYYY-MM' keys read in UTC (see [utils/month.ts](utils/month.ts)), **except the current month**: it is `currentMonthKey()`, from the phone's calendar. `monthKey(new Date())` reads UTC, which is already the next month from 21h on the last day in Brazil, while the transaction made then is dated with the local day and would disappear from the Dashboard. The functions that read a date in UTC and compare the day of the month (`buildSummary`, `generateInsights`) get `localNow()`, a Date whose UTC fields are the phone's own. Past months are compared with the whole of the month before them (`buildSummary` gets the last day of the month as `now`), and the tips only exist for the current month. The budget is stored on the server per month as the month it starts to apply from (`GET /budgets/monthly`; null = none from then on; the first version's budget comes as month `0000-00`) and [utils/budget.ts](utils/budget.ts) `budgetForMonth` picks the one in force, so changing it in Perfil only affects the current month onward. The history rows come from [utils/history.ts](utils/history.ts) (`buildHistory`, covered by its test) over `GET /reports/monthly-totals`.

**The month a spending counts in** ([docs/api-mes-do-gasto.md](docs/api-mes-do-gasto.md)): a purchase on credit counts in the month the invoice that receives it is **due** in (when the money leaves), anything else in the month of its day. The API stores it as `spendingMonth` in every transaction and `spendingMonthOf` (utils/invoice.ts) is the same rule on the phone, covered by the same cases as the server. Two kinds of month, on purpose: `useTransactions({ month })` is by the day (the Carteira, an account's statement, with the tag "Fatura dez" on a purchase on credit; the search) and `useTransactions({ spendingMonth })`, `useMonthTransactions`, `getMonthlyTotals` (`?by=spending`) are by the month it counts in: the Dashboard, the Detalhamento, the insights and the history. A month that has not started can already have purchases on credit registered in it, so for it the registered rows and what the recurring expenses plan (`plannedBySpendingMonth` in utils/plannedSpending.ts, which also feeds the "Próximos meses" of the history with `futureSpendingMonths`) are shown together. Comparing a month with the one before it "up to the same day" (`buildSummary`, `generateInsights`) uses `spendingDay` (the due day for a purchase on credit, set by the hook) instead of the day of the purchase. Changing the closing or due day of an account makes the server count its purchases on credit again, so the numbers of past months can change.

**Recurring expenses**: only expenses repeat (an income is not predictable). On the details step of a new expense, "Repetir" offers `none`, `monthly` or `installments` (total payments, and which one the person is on). That is **one** `POST /transactions` with `repeat`: the transaction made is the first occurrence (for installments, the one the person is on: the date asked is the purchase's and the app sends the day of that installment, `installmentPlan` in [utils/installments.ts](utils/installments.ts), so an old purchase in its 3rd of 4 lands in the right invoices; the installments before it are not registered, because they were paid in invoices the app never saw, and one that falls in an invoice after the open one is refused) and the **server** creates the rest when they fall due, whenever it reads (cards, transactions, recurrences, reports), so there is nothing to generate in the app; each recurrence remembers `generatedUntil`, so nothing is created twice and a generated transaction the person deletes stays deleted. The rules (due dates, a day 31 landing on the last day of short months, the last month of a plan, what an ended one still owes) are pure functions in [utils/recurrence.ts](utils/recurrence.ts), with their test, used by the app for what is only planned. A month that has not started (up to `FORECAST_HORIZON` = 6 months ahead) has no rows: `useTransactions`/`useCategoryTotals` return what the recurrences plan for it as rows with `planned: true` and a negative id, so every screen shows them with the same code (dashed, muted, "PREVISTO", not pressable) and none of it counts as a balance. `RecurrenceBadge` ("4/10" or "Todo mês") marks them in the lists. A transaction made by a recurrence shows a `RecurrenceCard` in its details with the way to end it (`endRecurrence` → `POST /recurrences/:id/end`; what was made stays); editing it can apply the change to the next ones (`applyToNext` in the same `PATCH`, and turning it into an income ends the recurrence: the server does both).

**Category limits, search and reminders**: (1) A spending limit per category, set in Detalhamento (`CategoryLimits`, `LimitSheet`), is stored on the server per month exactly like the monthly budget: the month it starts to apply from, `limitsForMonth` ([utils/categoryBudget.ts](utils/categoryBudget.ts)) picks what is in force, and it only edits from the current month on. `generateInsights` takes the limits and warns about the category furthest along from 80% of its limit. (2) The `search` route is a sheet opened from the Carteira list: the **server** looks (`GET /transactions?q=&type=&categoryId=`, every word must match the name, description, category or account, accents and case ignored, after the person stops typing for 300 ms), and every match is read when there is a filter, so the count and the total are exact; with none only the most recent are asked for. ([utils/search.ts](utils/search.ts) still has the old in-memory filter, no longer used, besides `netOf` and `TypeFilter`.) (3) Reminders: `buildReminders` ([utils/reminders.ts](utils/reminders.ts), pure) lists the occurrences of recurring expenses that fall due in the next 45 days and [db/reminders.ts](db/reminders.ts) (`refreshReminders`) schedules a local notification for each, the morning before at 9h, clearing the old ones first (nothing else in the app schedules notifications). It reads `/me` and the recurrences through the cache. `RecurrenceSync` runs it when the app opens with a session and when it returns to the foreground; it also runs after a recurrence is created, ended or edited, and when the switch in Perfil (`remindersEnabled`) is saved. The permission is asked when the switch is turned on and when the first recurrence is created. `expo-notifications` is a native module: changing its plugin options in `app.json` needs `expo prebuild` and a new build.

**Transfers between accounts**: made in the `transfer` sheet (opened from "Transferir" in the Carteira account summary, only with two or more accounts) with `POST /transfers`. A transfer is two ordinary transactions tied by a `transferId`: an expense in the account the money left and an income in the one it went to, in the hidden "Transferência" category (id `transfer`). The legs move the accounts' balances, but everything that adds up a month leaves them out: `withoutTransfers` ([utils/transfer.ts](utils/transfer.ts)) in `buildSummary`, `generateInsights`, the account's receitas/despesas and the Detalhamento list, and the server in `/reports/*`. They show in the lists with a neutral amount color. Their details have nothing to edit (one leg alone would unbalance the accounts): `TransferDetails` shows where the money left and went (the two legs are found among the transfers of that month, `getTransferLegs`), and deleting removes both legs (`deleteTransfer`, from either one). Deleting an account also deletes the other leg of every transfer it took part in.

**First-run tutorial**: the Home starts a four-card tutorial the first time an account opens it (`useTutorial`, [hooks/useTutorial.ts](hooks/useTutorial.ts); `TutorialOverlay` draws it): the screen is dimmed but for one thing at a time (the floating button, the balance card, the Carteira tab, the Detalhes tab) and a card says what it is for; Próximo and Pular (Voltar and Começar on the last one) are the controls, Android's Back goes a step back and every touch is blocked meanwhile. It is not a fixed picture: each target registers itself with `useTutorialTarget(id)` ([utils/tutorialTargets.ts](utils/tutorialTargets.ts) keeps them) and is measured on the window, and [utils/tutorial.ts](utils/tutorial.ts) (`layoutTutorial`, with its test) turns the rectangle into the hole, the four dim rectangles, the side of the card (above for a target in the lower half) and the arrow; a step whose target is not on screen is left out. It starts when the Home has loaded the current month, after a short wait, and only when the flag of that account is not set ([db/tutorial.ts](db/tutorial.ts), AsyncStorage `sobro:tutorial:v1:<account id>`: one for each account, since two people can share a phone). Skipping or finishing sets it; closing the app halfway does not, so it starts over. Perfil has "Rever tutorial" (`TutorialCard`), which clears the flag and goes to the Home. The copy and the steps are in [types/tutorial/tutorial-type.ts](types/tutorial/tutorial-type.ts); a new target is a `TutorialTargetId`, a `useTutorialTarget` on the view and a step. Every account that already existed sees it once after the update.

**Credit card and invoices**: an account can have a credit card (`CardRecord.credit`: limit, closing day, due day; it is turned on with the "Tem cartão de crédito" switch of the account form, and the last digits are the account's own `number`). Every expense asks "Como pagou" (`PaymentSection` in the new-expense flow, after the date and before Repetir; a row of `EditForm` in the details), on any account: Pix and debit are always there and leave the balance at once, while Crédito only shows on an account that has a card, and **credit stays out of the balance** (the server works the balance out without it) and goes into an invoice, and it counts as spending in the month its invoice is **due** in, not on the day of the purchase (see "The month a spending counts in" below). Every expense made before this existed has `paymentMethod: null` and just leaves the balance. The invoice is **not stored**: `buildInvoice` ([utils/invoice.ts](utils/invoice.ts), with its test) works it out from the credit purchases of its cycle and the payments, by the rule of [docs/api-cartao-credito.md](docs/api-cartao-credito.md): its key is the month it closes in (the one in the routes and in `invoiceMonth`) but it is shown by the month it is due in, the way the bank calls it (`invoiceName`, `invoiceNameWithYear`, `invoiceShortNameOf` in utils/invoice.ts: "Fatura dez" for the one that closes on 25/11 and is due on 05/12), a purchase up to the closing day goes into that month's invoice and a later one into the next, days are calendar days (`'YYYY-MM-DD'`, never a UTC instant) and a day past the end of a short month is its last day. `useInvoice` / `useOpenInvoice` read the calendar months its cycle touches (`getInvoiceSources`, with the `paymentMethod=credit` filter) plus the payments, and add what the recurring expenses on credit still plan (`plannedPurchases`, marked `planned`; they count in the invoice's `total`, with `plannedTotal` saying how much of it is only planned, while `remaining` is what was already bought and can be paid; the invoice screen can go ahead as far as `lastPlannedInvoice`, so a purchase in 10 payments shows in each of the next 10 invoices). Paying is `payInvoice` (`POST /cards/:id/invoice-payments`, in the sheet `payInvoice/[id]`, with the balance of the same account): an expense in the hidden category `invoice` with `invoiceMonth`, which moves the balance but, like a transfer, counts as no spending (`isInvoicePayment` / `isMoneyMove` in [utils/transfer.ts](utils/transfer.ts): `withoutTransfers` leaves both out and the lists draw them neutral). It is not edited, only undone (`InvoicePaymentDetails`). The account summary of the Carteira (`WalletSummary`) sums receitas and despesas of the list below it (the month by the day, the account in view), so the despesas include the purchases on credit; when there are any it says how much of them went on credit and how much left the saldo, and that the invoice adds up its own cycle. Carteira shows `InvoiceCard` under the account summary (the open invoice, and the previous one while it waits to be paid), the lists tag each credit purchase "Fatura nov", and `invoice/[id]` walks the invoices month by month. Detalhamento has an account filter ("Todas" or one account, shown with more than one account) that every figure below it follows, so its totals by category are summed on the phone from what counts in the month (`spendingByCategory`, [utils/spending.ts](utils/spending.ts), with its test; the same sum as `/reports/category-totals`) instead of read from that report; the budget bar and the category limits are for the whole account and only show with "Todas". `PaymentSplitCard` ("Como você pagou": Pix, débito, crédito and "Sem forma informada", from `spendingByPayment`) splits that same spending, so it always adds up to "Gastos do Mês", and only shows when at least one expense says how it was paid. The fields come from the API changes written in docs/api-cartao-credito.md: **until the server has them the app reads them as absent** (`credit` null, `paymentMethod` null) and none of this shows.

**Caixinhas (savings goals)**: a section of Carteira (`GoalsSection`, under the account summary) listing each caixinha with its progress (`GoalCard`), and how much of the money in the accounts is reserved and how much is free. A caixinha only reserves money that stays in the accounts: an entry (positive = put in, negative = taken out) moves no account balance and no month's income or expense, and what is in a caixinha (`saved`) is worked out by the server, never stored. A caixinha has a name, a target, an optional deadline month, a color and an icon. Tapping one opens the `goal/[id]` sheet (a `transparentModal` like `transfer`): Guardar / Retirar (`MovementModal`; only what is in it can come out: the server answers 409 `goal_insufficient` with how much there is, which shows inside the dialog), the history of entries, edit (`GoalFormModal`, also used to create from Carteira) and delete (the history goes, the money does not move). The rules are pure functions in [utils/goals.ts](utils/goals.ts) with their test: `goalProgress` (percent, what is missing, and with a deadline the months left counting the current one and the suggested amount per month), `totalReserved`, `freeBalance`, `movementProblem`. The sheet is `app/goal/[id].tsx`, its own components are in `app/goal/components/` (`MovementModal`, `MovementRow`), `GoalCard` and `GoalFormModal` are in `app/components/` because Carteira uses them too, and the copy is in `types/goal/goal-type.ts`.

**Backup**: Perfil has a "Seus dados" card (`BackupCard`) that exports and imports one JSON file, the format the first version of the app saved (`app: 'sobro'`, `schemaVersion` up to 9, which added the credit card of an account and how each expense was paid; the server takes any version from 1). Exporting is `GET /backup` shared through the share sheet ([db/backupFile.ts](db/backupFile.ts) does the device side: the file in the cache through `expo-file-system`'s `File`, the share sheet, the document picker). Importing reads the file, checks its shape with `validateBackup` ([utils/backup.ts](utils/backup.ts), with its test; `BACKUP_TABLES` in [utils/backup-type.ts](utils/backup-type.ts) lists the tables and columns) to show what is in it, asks the person to confirm with the counts (it replaces everything in the account) and sends the file **as it was read** with `PUT /backup`, which checks it again, replaces everything in one step (a refusal, 400 `invalid_backup`, says why and changes nothing) and makes every id again, so afterwards `resetAllData()` throws away the cache and the reminders are scheduled again. The server drops `theme`, `avatar_uri` and `monthly_budget` of the profile. Categories the person made (ids `custom-*`) travel in the file and come back with new ids.

**Categories**: the catalog (the same for everyone, read only) plus the ones the person makes (`custom-…`, created in the new-transaction flow with `NewCategoryModal`; only a person's own can be edited or deleted, and one in use cannot: 409 `category_in_use`). `useCategories` returns both; the hidden "Transferência" category is filtered by `categoriesForType`.

**Insights and tips**: generated on the device from the user's own transactions, with no extra call. [utils/insightRules.ts](utils/insightRules.ts) (`generateInsights`) is a pure function that compares the month with the same stretch of the previous one, and looks at the balance, the biggest category, a single heavy expense, category spikes and the month's pace; its thresholds and Portuguese copy live in [utils/insightRules-type.ts](utils/insightRules-type.ts) and months are read in UTC through [utils/month.ts](utils/month.ts). `useInsights()` (which also returns the two months it read, and `loading`/`error`) feeds the card on the Dashboard (the most relevant insight, warnings first) and the `insights` route, which is a sheet like `registrationSpent` (`transparentModal`, its own backdrop) listing all of them. To add a rule, add its copy to `INSIGHT_COPY`, push it from `generateInsights` and cover it in the test.
